Plug an analyzer into VISTA-MCP

VISTA-MCP is an MCP server whose tools are thin entry points into one config-driven orchestrator. It contains no per-analyzer code. If your service exposes the two endpoints on this page, it can be added to any tool from the console — no pull request, no deploy, no restart — and the orchestrator will discover it, decide when it is relevant, call it, and fold its report into the answer the agent receives.

1What you are building

An analyzer is an ordinary HTTP service. It receives a file (plus whatever else it declares) and returns one finished markdown report. It does its own AI/analysis internally — VISTA-MCP never second-guesses it, never re-formats its text, and never calls ORB on its behalf.

MCP client→ VISTA-MCP→ GET /discover→ AI Controller decides + plans→ POST <query.path>→ concatenate + ORB→ one report
Both endpoints are plain HTTP + JSON. No auth is assumed between the orchestrator and analyzers on the internal network (mTLS or a token can be added later without changing these shapes).

2The two endpoints

PurposeMethod + pathReturns
Discovery — what you are + how to call you GET <base>/discover AnalyzerDiscovery
Query — do the analysis POST <query.path> AnalyzerResult

<base> is the URL an operator types into the console. <query.path> is whatever your discovery advertises — it need not live under <base>. The only path VISTA-MCP hardcodes is /discover. Everything else it learns from you, on every call.

GET <base>/discover → AnalyzerDiscovery

{
  "schema_version": "1.0",
  "surface": "analyzer",
  "base_url": "http://host/perf",
  "analyzer": {
    "id": "perf",                       // stable short id (also the id used in the tool config)
    "title": "Performance Analyzer",
    "summary": "One-line description.",
    "when_to_use": "The text the AI Controller reads to decide. Be specific: say exactly which
                    questions this analyzer answers and which it does NOT.",
    "input_types": ["FortiOS/FortiGate log or config file"],
    "supported_log_types": []           // optional; [] = not log-type specific
  },
  "query": {
    "method": "POST",
    "path": "http://host/perf/run",     // fully-qualified, ready to call
    "content_type": "multipart/form-data",
    "params": [
      { "name": "file",     "required": true,  "type": "file",   "location": "file",
        "description": "The file to analyze." },
      { "name": "question", "required": false, "type": "string", "location": "form",
        "description": "The user's natural-language question (optional)." },
      { "name": "mode",     "required": true,  "type": "string", "location": "form",
        "default": "quick",
        "description": "Analysis depth: 'quick' for a fast scan, 'deep' for a full correlation
                        pass. Choose 'deep' when the question names a specific device or metric." }
    ],
    "response": "AnalyzerResult"
  }
}
FieldWhy it matters
analyzer.when_to_use critical The single most important field. It is exactly what the AI Controller reads to decide whether your analyzer is relevant to a question. Write it like a routing rule: “Use for … / do NOT use for …”. A vague one gets you called too often or never.
query.path required Must be a fully-qualified URL. This is the only endpoint that will ever be called.
query.params[] required Declare every param you accept. A param you don't declare will never be sent — the orchestrator refuses to send anything you didn't advertise.
params[].description Read by the AI Controller when it has to choose a value. Describe the allowed values and when each applies (see mode above) and it will pick sensibly.
params[].default The value to send when nobody has a better one. If you add a required param, give it a default — that keeps working even when the AI gateway is unreachable.
params[].location "file" for the uploaded file, "form" for everything else.

Extra fields are allowed and ignored (forward-compatible). An ApiResponse envelope ({ok, kind, data:{…}}) is tolerated: if the top level has no analyzer key but has a dict data, the orchestrator reads data.

POST <query.path> → AnalyzerResult

A multipart request built from exactly what you declared. You return:

{
  "schema_version": "1.0",
  "ok": true,
  "analyzer_id": "perf",
  "title": "Performance Analyzer",              // section heading in the combined report
  "report_markdown": "# Performance Analyzer\n\n…your finished contribution…",
  "artifacts": { "session_id": null, "view_url": null, "iframe_url": null },   // optional extras
  "meta": { "log_type": "System:sdwan", "elapsed_ms": 1234, "total_logs": 29169 },
  "error": null
}
report_markdown is the contract. It is your finished, human-readable contribution — format it completely, including your own heading. The orchestrator joins each analyzer's report_markdown with a horizontal rule and never rewrites it.
  • Always return 2xx with ok where you can. On a handled error return ok:false with a short error and a one-line report_markdown explaining it — don't 500. (The orchestrator is fail-soft either way, but a clean result is friendlier to the engineer reading the answer.)
  • Reduce, don't dump. Your text lands in an agent's context window. The heavy reduction is your job.
  • meta is free-form and is stored per job — elapsed_ms, log_type, counts and “supported” flags all show up in the console.
  • Don't call ORB. The orchestrator adds ORB troubleshooting once, at the very end.

3Copy-paste models

Your service only has to emit these shapes. Copy them into your project:

from pydantic import BaseModel, Field
from typing import Any

class AnalyzerParam(BaseModel):
    name: str; required: bool = False
    type: str = "string"        # "string" | "file"
    location: str = "form"      # "form" | "file"
    description: str = ""       # the AI Controller reads this when choosing a value
    default: str = ""           # value to send when nobody has a better one

class AnalyzerQuery(BaseModel):
    method: str = "POST"
    path: str                   # fully-qualified URL
    content_type: str = "multipart/form-data"
    params: list[AnalyzerParam] = Field(default_factory=list)
    response: str = "AnalyzerResult"

class AnalyzerInfo(BaseModel):
    id: str; title: str; summary: str = ""; when_to_use: str = ""
    input_types: list[str] = Field(default_factory=list)
    supported_log_types: list[str] = Field(default_factory=list)

class AnalyzerDiscovery(BaseModel):
    schema_version: str = "1.0"; surface: str = "analyzer"; base_url: str = ""
    analyzer: AnalyzerInfo; query: AnalyzerQuery

class AnalyzerResult(BaseModel):
    schema_version: str = "1.0"; ok: bool = True
    analyzer_id: str = ""; title: str = ""; report_markdown: str = ""
    artifacts: dict[str, Any] = Field(default_factory=dict)
    meta: dict[str, Any] = Field(default_factory=dict)
    error: dict[str, Any] | None = None

4A complete analyzer, start to finish

Everything needed to be callable by VISTA-MCP, in one file:

from fastapi import FastAPI, File, Form, Request, UploadFile
from fastapi.responses import JSONResponse

app = FastAPI()
BASE = "/perf"

@app.get(f"{BASE}/discover")
def discover(request: Request):
    root = str(request.base_url).rstrip("/")
    return {
        "schema_version": "1.0",
        "surface": "analyzer",
        "base_url": f"{root}{BASE}",
        "analyzer": {
            "id": "perf",
            "title": "Performance Analyzer",
            "summary": "FortiGate CPU/memory/conserve-mode analysis.",
            "when_to_use": (
                "Use for FortiGate performance questions — CPU or memory pressure, conserve "
                "mode, session or resource exhaustion. Do NOT use for routine SLA, traffic or "
                "event-log questions."
            ),
            "input_types": ["FortiOS/FortiGate log file"],
            "supported_log_types": [],
        },
        "query": {
            "method": "POST",
            "path": f"{root}{BASE}/run",
            "content_type": "multipart/form-data",
            "params": [
                {"name": "file", "required": True, "type": "file", "location": "file",
                 "description": "The file to analyze."},
                {"name": "question", "required": False, "type": "string", "location": "form",
                 "description": "The user's question (optional)."},
            ],
            "response": "AnalyzerResult",
        },
    }

@app.post(f"{BASE}/run")
async def run(file: UploadFile = File(...), question: str = Form("")):
    data = await file.read()
    report = analyze(data, question)          # ← your logic; returns finished markdown
    return JSONResponse({
        "schema_version": "1.0", "ok": True,
        "analyzer_id": "perf", "title": "Performance Analyzer",
        "report_markdown": report,
        "artifacts": {}, "meta": {"bytes": len(data)}, "error": None,
    })

Two working references ship with the repo: fakes/fake_analyzer.py (the shape above) and fakes/fake_analyzer_v2.py (the same contract with a deliberately different request shape — see §6).

5How VISTA-MCP uses your discovery

DISCOVER   GET <base>/discover                      → your contract        (every run, concurrent)
DECIDE     AI Controller reads analyzer.when_to_use  → call this analyzer?
PLAN       AI Controller reads query.{method,path,content_type,params}
                                                     → a request plan for this call
VALIDATE   the plan is checked field-by-field against your discovery document
CALL       execute the plan                          → your AnalyzerResult (concurrent)
CONCAT     join every report_markdown with a horizontal rule
ORB        (once, if the tool enables it) appended as "## ORB Suggestions"

Three consequences worth knowing:

  • Your discovery is fetched on every call, not cached from yesterday. What you advertise now is what gets used now.
  • The AI Controller never skips — even for a tool whose analyzers are all mandatory it still runs, precisely so a contract change is noticed the moment it happens.
  • The model proposes; your document decides. A proposed request is validated against your discovery: an undeclared field, an unadvertised path, a foreign host or a wrong verb is corrected or dropped before anything is sent, and the correction is recorded on the job.
Fail-safe: if the AI gateway is down, the orchestrator runs every optional analyzer and builds each request straight from your discovery. Required params fall back to their default — which is why declaring one matters.

6Changing your API later

This is the point of reading discovery on every call. You may:

ChangeWhat VISTA-MCP doesWhat you should do
Rename the file param (file → payload) attaches the file to the newly declared file paramjust declare it
Rename the question param (question → query) sends the question to the new namekeep description clear
Move the endpoint (/run → /v2/analyze) calls the newly advertised query.path keep the old path alive briefly if other clients exist
Add an optional param omitted unless the AI Controller sees a reason to set it describe when it matters
Add a required param the AI Controller picks a value from your description; the no-AI path sends your default always give it a default
Switch to application/json sends a JSON body built from your declared params note that a JSON body carries no file
None of these need a VISTA-MCP change, a restart, or a config edit. Ship your new discovery document and the very next call follows it.

What a caller will never do, by design: send a param you didn't declare, call a path you didn't advertise, or use a verb or host you didn't advertise.

7Register it — no code, no restart

  1. Open the console → ⚙ Add / Edit Tools.
  2. Find the tool your analyzer belongs to (or ＋ New tool to create one).
  3. ＋ add analyzer, paste your base URL, press 🔌 Test & autofill. The console calls your /discover, confirms the contract, fills in id and title, and shows your when_to_use back to you.
  4. Pick the role:
    • mandatory — always called for this tool.
    • optional — called only when the AI Controller judges it relevant.
  5. Save & reload. Live immediately.

The same thing by hand, in config/tool_enablement.json:

{
  "id": "perf",
  "title": "Performance Analyzer",
  "api_url": "https://vista.fortinet.com/perf",
  "discover_url": "",          // empty ⇒ derived as api_url + "/discover"
  "mandatory": false,          // false ⇒ the AI Controller decides per question
  "enabled": true,
  "timeout": 120
}

8Checklist & testing

  • GET <base>/discover returns 200 with a valid AnalyzerDiscovery
  • when_to_use reads like a routing rule, including what not to use it for
  • every param is declared, with a description
  • every required param has a default
  • query.path is fully qualified and reachable from the VISTA-MCP host
  • the query endpoint returns AnalyzerResult with a fully-formatted report_markdown
  • handled errors return ok:false + a one-line report, not a 500
  • your own timeout is below the timeout configured for you in the tool
  • 🔌 Test & autofill goes green in the console

Verify by hand before registering:

# 1. discovery is valid JSON and advertises your query path
curl -s https://your-host/perf/discover | python3 -m json.tool

# 2. the endpoint it advertises actually works
curl -s -X POST https://your-host/perf/run \
     -F 'file=@sample.log' -F 'question=High CPU and conserve mode' | python3 -m json.tool

# 3. the console agrees (from the VISTA-MCP host)
curl -s -X POST http://127.0.0.1:8100/gui/api/probe \
     -H 'Content-Type: application/json' -d '{"url":"https://your-host/perf"}'

After the first real call, open the job in the console and click your analyzer's node: the Request sent block shows exactly what arrived at your service, and Live discovery document shows the contract that produced it.

9FAQ

Does my analyzer have to take a log file?

No. Declare whatever params you accept. If you declare no file param and a JSON content type, you get a JSON body built from your declared params.

Can I be called by more than one MCP tool?

Yes — add the same analyzer to as many tools as you like. Each tool decides independently whether you are mandatory or optional, and each has its own routing prompt.

What happens if I'm slow or down?

Fail-soft. If /discover doesn't answer you are dropped for that run and the other analyzers proceed. If the call fails or times out (per-analyzer timeout), the other analyzers still answer and your section is replaced by a short error note.

Who calls ORB?

The orchestrator, once, at the very end, using the combined report. Analyzers must not.

How do I know whether the AI Controller is choosing me?

The console's Dashboard → By analyzer shows how often you were selected, called, and succeeded. If you're never selected, sharpen when_to_use; if you're selected too often, say explicitly what you are not for.
