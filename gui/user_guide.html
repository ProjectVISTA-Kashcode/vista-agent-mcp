Using the VISTA-MCP console

The operator surface for the orchestrator. Watch every job execute step by step, see exactly what each analyzer was sent and returned, search the whole history, and add or change tools, analyzers and routing prompts — without touching code or restarting the server.

1What this console is

VISTA-MCP is an MCP server. A partner agent calls one of its tools with a log file and a question, and gets back one text report. Behind that single call is a pipeline: discover the available analyzers, decide which ones this question needs, call them in parallel, combine their reports, and append ORB troubleshooting.

This console shows you that pipeline — live and historically — and lets you change it.

ViewWhat it's for
⛓ FlowThe live canvas — one job or one tool's template, animating as it runs
📈 DashboardAnalytics over the stored history: volume, success rate, latency, per-tool and per-analyzer behaviour, errors
🗂 HistoryThe searchable permanent record — find any job from any point in the past and replay it
Everything you change here is written to config/tool_enablement.json, validated, hot-reloaded into the running server, and audited to the database.

2What a job actually does

📥 intake→ 🧭 VFR→ ⚙️ tool enablement→ 🔎 discover→ 🧠 AI Controller→ 📊 analyzers (parallel)→ 🧩 concat→ 🛟 ORB→ ✅ answer
NodeWhat happens
Tool Call & FetchThe MCP call as received, plus the log fetched from the platform-injected source_url.
VFR (routing)Vetting & flow routing — a pre-flight file check. A passthrough today; the seam is in place for real logic.
Tool EnablementThis tool's config: which analyzers exist, which are mandatory, whether ORB runs.
Discover ToolsGET /discover on every configured analyzer, concurrently. This is where each analyzer's current API contract comes from.
AI ControllerPicks which optional analyzers to add and plans how to call each one, from the contract just discovered. Runs on every job — see §8.
Analyzer nodesThe selected analyzers, called in parallel. Each returns a finished markdown section.
ConcatenateEvery analyzer's report joined with a horizontal rule. Nothing is rewritten.
ORB SuggestionsTroubleshooting, asked once at the end with the combined report + the user's question. Fail-open.
Answer & BackThe single text report handed to the MCP client.

3Flow view

  • Tool tabs (top) preview a tool's flow shape before any job runs — its analyzers, whether ORB is on, whether it has a custom routing prompt.
  • Recent jobs (left) lists in-flight and past runs, newest first, straight from the database — so it survives a restart. Scroll to the bottom for a button into the full History.
  • Canvas — drag to pan, scroll to zoom, double-click empty space to fit, or use the −/+/fit/100% controls at the bottom right.
  • Click any node to open the inspector.
A red pulsing node is running; green is done; amber is skipped; red-filled is an error. Edges animate while the step downstream of them is running.

4The node inspector

Clicking a node answers “what did this step actually do?”. What you see depends on the node:

AI Controller

  • mode — select+plan (there were optional analyzers to choose from) or plan-only (nothing to choose, but the live contracts were still read).
  • AI answered — yes, or fail-safe if the gateway didn't respond.
  • plan source — ai, ai-corrected or deterministic.
  • Planned calls — for every analyzer: the request URL, which param carries the file, which fields were sent, the model's own note, and any corrections validation applied.
  • Routing system prompt and Raw AI answer — the full audit trail.

Analyzer nodes

  • Request sent — the exact method, URL, content type, file param and fields.
  • when_to_use — the text the AI Controller read when deciding about this analyzer.
  • Live discovery document — the analyzer's whole contract at the moment it was called.
  • Result meta and this analyzer's report — what came back.
Every expandable block has a ⤢ button that opens it in its own window — handy for long discovery documents and reports, and it stays open while the job keeps updating.

5The CLI log

The bottom drawer mirrors the server terminal for the selected job.

  • Drag its top edge to resize (the height is remembered), or collapse it with ▾.
  • Filter by free text, or by status (running / ok / skipped / error).
  • verbose adds an expander to every line — click ▸ N fields to see that event's structured payload.
  • 📄 report opens the exact text the MCP client received. copy copies the log.

Each line carries a wall-clock time and a relative offset from the start of the job, so you can see immediately where the time went.

6Add a new MCP tool

A “tool” is what the MCP client sees in list_tools. It gets its own flow, its own analyzers and its own routing prompt — and it becomes callable the moment you save.

1
⚙ Add / Edit Tools → ＋ New tool (or the ＋ add tool chip in the tool bar) opens the guided wizard.
2
Give it a name — this is the exact list_tools name agents call (letters, digits, _, -) — and a description the calling agent reads to decide whether to call it. Say what it does and that the platform injects the file.
3
Write its routing prompt (guidance for the AI Controller when choosing optional analyzers — the JSON output contract is appended automatically, so write freely) and choose whether ORB troubleshooting is appended to its report.
4
Add its analyzers — paste a base URL, hit 🔌 Test & autofill, mark each mandatory or optional — then Create tool.

On save the server validates the config, writes it, re-registers the live MCP tool set and records an audit row. The tool is in list_tools immediately, has its own flow, and appears under Integrations. No restart.

7Add an analyzer to an existing tool

⚙ Add / Edit Tools → find the tool → ＋ add analyzer → paste the base URL → 🔌 Test & autofill.

The probe calls GET <base>/discover and shows the analyzer's when_to_use — the single most important field, because that is exactly what the AI Controller reads when deciding whether to call it. Then pick the role:

  • mandatory — always called for this tool.
  • optional — called only when the AI Controller judges it relevant to the question.
Nothing else is needed. Discovery, selection, invocation planning, the parallel call, concatenation and ORB all work with your analyzer immediately — as long as it speaks the standard contract. Building one? See the API Integration Guide.

What gets validated before a save

  • tool names match [A-Za-z0-9_-], up to 64 characters
  • every analyzer has an id and an http(s) api_url
  • no duplicate analyzer ids inside a tool
  • every tool has at least one enabled mandatory analyzer — otherwise a call could run nothing

If validation fails the file on disk is left untouched and the message names the problem. ⟷ Raw JSON switches the editor to the underlying config and back, for bulk edits.

8What the AI Controller does

It runs on every job — never skipped — and does two things:

  1. Selects which optional analyzers to add, from each one's when_to_use.
  2. Plans the call for every analyzer that will run, from the contract that analyzer just advertised: method, URL, content type, which param carries the file, which declared params get the question.

That is why an analyzer can rename a param, add a required field or move its endpoint and keep working with no change here — and why a brand-new analyzer added minutes ago is called correctly the first time.

The model proposes; the discovery document decides. Every plan is validated field-by-field before anything is sent — an undeclared field, an unadvertised path, a foreign host or a wrong verb is corrected or dropped, and the correction is listed on the node. If the AI gateway is unavailable the orchestrator falls back to the deterministic policy: run every optional analyzer, build each request straight from discovery.

9Dashboard

Filter by time range, tool, analyzer, status, AI usage and ORB outcome, plus free text. The filter summary line always states exactly what you're looking at, and Reset clears it.

  • KPI tiles — jobs, success rate, median duration (with p95 and max), how often the AI Controller answered and how often its plans were used as-is, ORB coverage, report volume and bytes analyzed. Click a tile to jump to History with the same filters applied.
  • Jobs over time — volume per bucket with errors overlaid and average duration as a line.
  • By tool — volume, errors and average duration. Click a row to filter by that tool.
  • By analyzer — how often each was selected, its OK/failed counts, average call time, and how many of its requests the AI Controller planned. A rising correction count is the signal that an analyzer's contract has drifted.
  • Recent errors — click any row to open that job's flow.

10History

The permanent record. Every job is stored with its whole flow: each step, each analyzer's discovery document and the exact request it received, ORB, and the final report.

Filter by free text (question, filename, job id, tool), tool, status, analyzer, time range, and whether the AI Controller answered. Click any row to replay that job's flow — nodes, inspector and CLI log exactly as they were, reconstructed from the database even if the server has restarted or the job was produced by a different instance.

12Troubleshooting

What you seeWhat it means
“dropped” on the Discover node That analyzer's /discover didn't answer, so it was skipped for this run. Use 🔌 Test & autofill in the editor to see the exact error.
AI badge says fail-safe The AI gateway didn't answer. Every optional analyzer ran and each request was built from discovery — the job completed normally, it just had no judgement applied.
plan corrected notes on a node The model proposed something the analyzer never advertised; the orchestrator replaced it with the discovered value. Each change is listed.
An analyzer node is red That analyzer failed or timed out. The others still answered — its section is replaced by a short error note. Check the HTTP status in the inspector.
Dashboard/History say “not connected” DATABASE_URL isn't set or the database is unreachable. The live Flow view still works; see docs/db_setup.md.
Save rejected The config failed validation. Nothing was written; the message names the field.
“reconnecting…” in the header The page can't reach the server. It retries every 1.5 s.

13Security

The console is not behind the MCP bearer token — it is a local operator tool. Bind the server to localhost or a trusted network, or front it with your own auth. Two routes are not read-only:

  • POST /gui/api/config — validates before writing, and records an audit row (who, when, what).
  • POST /gui/api/probe — performs a server-side GET on the URL you type (http/https only), so the editor can confirm an analyzer's contract.
